# Demo mode (GitHub Pages)

The live demo at https://cwbudde.github.io/studio-schedule/ runs **without any server**. GitHub Pages
only serves static files, and we don't host a backend for the demo. Instead:

1. The Go application (`cmd/wasm`) is compiled with `GOOS=js GOARCH=wasm`. This is the **same**
   `internal/app.New` handler, services and HTTP API as the production server.
2. The browser starts it in a **Web Worker**. The Worker loads `wasm_exec.js` (copied from the Go
   toolchain that built the binary) and `app.wasm`.
3. The Go side registers `globalThis.StudioScheduleAPI.fetch(request) → Promise<response>`. Each call
   becomes an `*http.Request` that is served by the handler in its own goroutine.
4. The React app uses the same generated `openapi-fetch` client as in production, but with a custom
   `fetch` that posts requests to the Worker. A small cookie jar in the Worker stores `Set-Cookie`
   headers, so session cookies behave as in a real browser–server setup.

## Differences from a real installation

| Aspect     | Production                  | Demo                                                            |
| ---------- | --------------------------- | --------------------------------------------------------------- |
| Database   | PostgreSQL                  | **In-memory store**, seeded with fictional data on every start  |
| Demo dates | Fixed school year 2026/27   | **Relative to the day of the visit** (see below)                |
| Lessons    | Generated by the hourly job | Same job: once before the first request, then hourly            |
| Durability | Persistent                  | **Lost on reload** (an optional IndexedDB snapshot is planned)  |
| Email      | SMTP via outbox worker      | Outbox only; shown in the demo mailbox panel                    |
| Passwords  | argon2id, production params | Cheap parameters so login is fast in WASM; seeded demo accounts |
| Sign-in    | Registered accounts         | The login page lists one demo account per role                  |
| Downloads  | Plain links (iCal, PDF)     | Fetched through the bridge and opened as Blob URLs              |
| Routing    | Browser history             | Hash history (`/#/…`), because Pages has no SPA fallback        |
| Timezone   | Host tzdata or embedded     | Embedded `time/tzdata`                                          |

Everything else, including validation, permissions, booking rules, the release window, receipts and
the API, is the same code.

## Seed data relative to the visit

The web demo's store lives only as long as the page, so `cmd/wasm` seeds it for the day of the visit
(today in the school time zone, from the app's clock): `seed.LoadDemoAt(ctx, st, today)`. The demo
term runs from three weeks before that day to about ten months after it, class members join on the
term's first day, and three one-off public workshops follow 3, 17 and 24 days after it. The demo
releases one week ahead, so the later workshops always lie beyond the release window; they are visible
because workshops are published early. `scripts/wasm-smoke.mjs` checks this.

The server (`studio-schedule serve` with the memory store) and `studio-schedule seed` use
`seed.LoadDemo`, which builds the same data for the fixed `seed.FixedDemoAnchor`: the term is the
school year 2026-09-01 to 2027-07-31 on every run, and its workshops lie in September and
October 2026. Only the dates differ between the two; names, IDs and the timetable are the same.

## Accounts and mail in the demo

The demo is a _demo installation_ (`app.Deps.Demo`, also set for `serve` without a database):

- **Demo accounts:** every seeded account has the published password `demo-password`, and
  `GET /api/v1/demo/logins` lists one account per role (member, instructor, office, admin) for the
  login page.
- **Mailbox:** nothing is ever delivered. `GET /api/v1/demo/mailbox` lists the outbox, and the
  mailbox panel in the header shows it, so a visitor can register, open the confirmation link and
  sign in.
- **What each role sees:** the demo data has one workshop for members only and one hidden workshop
  (staff only), a few days after the visit date. Signing in as the demo member, instructor or admin
  shows the difference. The admin can open Accounts and "sign in as" another account; a banner
  leads back ([ADR 0005](decisions/0005-rbac-and-impersonation.md)).
- **Mail links:** the Worker passes the app's URL (with the `#/` route prefix) to Go as the
  `APP_URL` environment variable.

Real installations answer both endpoints with 404
([ADR 0004](decisions/0004-accounts-sessions-and-mail.md)).

## Building it locally

```sh
just demo-serve        # = scripts/build-wasm.sh + vite build --mode demo + vite preview
```

Open the printed URL, for example `http://localhost:4173/studio-schedule/`.

## End-to-end tests

`just e2e` builds the demo and runs the Playwright tests in `web/e2e` against it through
`vite preview`: the real WASM backend in its Worker, in Chromium at desktop and phone size, with
the browser in `America/New_York` so school times cannot fall back to the browser's zone. They
cover the home page, the schedule list and week grid, filters, the lesson sheet, the release
countdown, early-published workshops, deep links and German. Any console error fails a test. The
`test-e2e` CI job runs them on every push and uploads the Playwright report when they fail. Run
`just e2e-install` once to download the browser.

Lessons are generated with random IDs on every start, so a link to a lesson works only within the
visit that produced it. Generation creates only lessons that have not started (ADR 0003); the seed
brings the lessons of the week before the visit, so the schedule has a recent past.

## Constraints to keep in mind

- `cmd/wasm` must not import server-only packages (database drivers, SMTP, CLI, `os/exec`,
  `httptest`). `scripts/check-wasm-deps.sh` enforces this in CI.
- Go's WASM runtime is single-threaded. CPU-heavy work blocks the Worker (not the UI), so keep
  request handlers cheap.
- A panic that escapes recovery terminates the Go program. The UI then shows "Demo crashed —
  reload".
- The binary size is reported in every CI run (`test-web` job summary).
