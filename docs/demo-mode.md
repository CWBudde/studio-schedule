# Demo mode (GitHub Pages)

The live demo at https://cwbudde.github.io/studio-schedule/ runs **without any server**. GitHub Pages
only serves static files, and we don't host a backend for the demo. Instead:

1. The Go application (`cmd/wasm`) is compiled with `GOOS=js GOARCH=wasm`. This is the **same**
   `internal/app.New` handler, services and HTTP API as the production server.
2. The browser starts it in a **Web Worker**. The Worker loads `wasm_exec.js` (copied from the Go
   toolchain that built the binary) and `app.wasm`.
3. The Go side registers `globalThis.StudioScheduleAPI.fetch(request) → Promise<response>`. Each call
   becomes an `*http.Request` that is served by the handler in its own goroutine.
4. The React app uses the same generated `openapi-fetch` client as in production, but with a custom
   `fetch` that posts requests to the Worker. A small cookie jar in the Worker stores `Set-Cookie`
   headers, so session cookies behave as in a real browser–server setup.
5. The Worker saves the whole in-memory store and its cookie jar in IndexedDB after every change, so
   a reload keeps the data and the session until the visitor resets the demo (see below).

## Differences from a real installation

| Aspect     | Production                  | Demo                                                             |
| ---------- | --------------------------- | ---------------------------------------------------------------- |
| Database   | PostgreSQL                  | **In-memory store**, seeded with fictional data on a fresh start |
| Demo dates | Fixed school year 2026/27   | **Relative to the visit that seeded the data** (see below)       |
| Lessons    | Generated by the hourly job | Same job: once before the first request, then hourly             |
| Durability | Persistent                  | **Kept in the browser (IndexedDB) until "Reset demo"**           |
| Email      | SMTP via outbox worker      | Outbox only; shown in the demo mailbox panel                     |
| Passwords  | argon2id, production params | Cheap parameters so login is fast in WASM; seeded demo accounts  |
| Sign-in    | Registered accounts         | The login page lists one demo account per role                   |
| Downloads  | Plain links (iCal, PDF)     | Fetched through the bridge and opened as Blob URLs               |
| Routing    | Browser history             | Hash history (`/#/…`), because Pages has no SPA fallback         |
| Timezone   | Host tzdata or embedded     | Embedded `time/tzdata`                                           |

Everything else, including validation, permissions, booking rules, the release window, receipts and
the API, is the same code.

## Seed data relative to the visit

On a fresh start (the first visit, after "Reset demo", or after a new build) `cmd/wasm` seeds the
store for the day of the visit (today in the school time zone, from the app's clock):
`seed.LoadDemoAt(ctx, st, today)`. A later visit restores the saved data instead, with the dates of
the visit that seeded it: the term and workshops do not move along, and after a few weeks the
workshops lie in the past. "Reset demo" seeds again for today; the banner says so. The demo
term runs from three weeks before that day to about ten months after it, class members join on the
term's first day, and three one-off public workshops follow 3, 17 and 24 days after it. The demo
releases one week ahead, so the later workshops always lie beyond the release window; they are visible
because workshops are published early. `scripts/wasm-smoke.mjs` checks this.

The server (`studio-schedule serve` with the memory store) and `studio-schedule seed` use
`seed.LoadDemo`, which builds the same data for the fixed `seed.FixedDemoAnchor`: the term is the
school year 2026-09-01 to 2027-07-31 on every run, and its workshops lie in September and
October 2026. Only the dates differ between the two; names, IDs and the timetable are the same.

## Saved data and "Reset demo"

The demo keeps what a visitor does across reloads, in their browser only:

- **What is saved:** a snapshot of the complete in-memory store (`memory.Store.Snapshot`, every
  table) and the Worker's cookie jar (the session), as the record `current` in the IndexedDB
  database `studio-schedule-demo` (`web/src/api/wasm/persistence.ts`). Cookies that do not have the
  expected shape are dropped on restore.
- **When:** after every committed change. `memory.Store.OnCommit` runs after each read-write
  transaction that wrote something (by a request or a background job, e.g. the lessons the
  generation job creates); `cmd/wasm` passes `wasmbridge.NotifyChanged`, which calls the Worker's
  `__studioScheduleChanged()`. A response that sets a cookie counts too. Saves are debounced by
  250 ms, so a burst of changes is saved once, and the page asks the Worker to save at once when it
  is hidden or closed (`pagehide`, `visibilitychange`; best effort). The Go side encodes the
  snapshot through `StudioScheduleAPI.snapshot()`: it copies the copy-on-write tables under the
  store's lock and encodes them without it, in one streaming pass.
- **When saving fails** (no quota, IndexedDB blocked in a private window), the visitor sees one
  notice that changes will not survive a reload. When the Go program has exited, the Worker stops
  saving (no misleading notice).
- **Restore:** on start the Worker claims the saved data (below) and reads the record before it
  starts Go, and hands the store to it as `globalThis.__studioScheduleSnapshot`. If IndexedDB fails
  or does not answer within three seconds, the demo starts from the seed, saves nothing, and shows
  the notice. `cmd/wasm` restores it before anything reads the store
  and before the jobs run, and reports `StudioScheduleAPI.restored`. Only then does the Worker load
  the saved cookies and answer requests.
- **Versions:** a snapshot fits only the build that wrote it. Its header names the build version
  (`main.version`) and a fingerprint of the store's Go types (every table and domain struct), plus
  the snapshot's own format version. `memory.Store.Restore` refuses any other
  (`memory.ErrSnapshotMismatch`): the demo then starts fresh from the seed, and the Worker deletes
  the old record, saved session included.
- **Format:** JSON (`encoding/json/v2`), which the WASM binary links anyway, so persistence adds no
  code to it. Each table is a list of its rows; keys are derived again on restore.
- **Completeness:** every field of the memory store's state needs a codec in
  `internal/store/memory/snapshot.go`; `TestSnapshotCoversEveryTable` fails for a table without one,
  and `TestSnapshotRoundTrip` restores the full demo data (plus a row in each table the seed leaves
  empty) and compares every table.
- **Reset demo:** the button in the header (and on the "Demo crashed" card) asks first, then stops
  the Worker, deletes the record from the page itself (so a crashed or hanging Worker cannot block
  it), and reloads. The demo starts fresh from the seed, for today, signed out. If the delete fails
  or takes longer than five seconds, the page reloads anyway and says that the reset failed.
  Nothing else expires the saved data.
- **One tab at a time:** all tabs of the origin share the IndexedDB record, so only one tab runs the
  demo: it holds the Web Lock `studio-schedule-demo` (`web/src/api/wasm/tabLock.ts`). Another tab
  shows "The demo is open in another tab" with "Use here": it asks the active tab over a
  `BroadcastChannel` to save (it waits up to 4.5 s for that save), stop its Worker and release the
  lock, then reloads into the demo. The previous tab shows the same notice. A tab that does not
  answer within five seconds (frozen in the background) loses the lock by force and stops when it
  runs again. A starting tab waits up to 1.5 s for the lock before it shows the notice, so a reload
  does not trip over its own previous page. Only the tab that holds the lock shows "Reset demo".
  Without Web Locks every tab runs its own demo.
- **Fencing:** in case a tab that lost the lock still saves (it was frozen during the takeover), each
  Worker claims the data on start: one transaction increments the epoch in the record `owner` and
  reads `current`. A save checks, in the same transaction as its write, that `owner` is still its
  epoch; otherwise it is refused and that Worker stops saving. A reset deletes only `current`, so
  stale saves stay refused.
- **The session cookie in IndexedDB:** GitHub Pages serves every project of a user from one origin
  (`cwbudde.github.io`), so other pages there could read the record, cookie included. This is
  acceptable because everything in the demo is fictional and the token opens only that browser's
  own in-memory demo; a real installation never stores sessions this way.

A demo server over HTTP (`serve` without a database) keeps nothing in the browser and has no reset
button.

## Accounts and mail in the demo

The demo is a _demo installation_ (`app.Deps.Demo`, also set for `serve` without a database):

- **Demo accounts:** every seeded account has the published password `demo-password`, and
  `GET /api/v1/demo/logins` lists one account per role (member, instructor, office, admin) for the
  login page.
- **Mailbox:** nothing is ever delivered. `GET /api/v1/demo/mailbox` lists the outbox, and the
  mailbox panel in the header shows it, so a visitor can register, open the confirmation link and
  sign in.
- **What each role sees:** the demo data has one workshop for members only and one hidden workshop
  (staff only), a few days after the visit date. Signing in as the demo member, instructor or admin
  shows the difference. The admin can open Accounts and "sign in as" another account; a banner
  leads back ([ADR 0005](decisions/0005-rbac-and-impersonation.md)).
- **Mail links:** the Worker passes the app's URL (with the `#/` route prefix) to Go as the
  `APP_URL` environment variable.

Real installations answer both endpoints with 404
([ADR 0004](decisions/0004-accounts-sessions-and-mail.md)).

## Building it locally

```sh
just demo-serve        # = scripts/build-wasm.sh + vite build --mode demo + vite preview
```

Open the printed URL, for example `http://localhost:4173/studio-schedule/`.

## End-to-end tests

`just e2e` builds the demo and runs the Playwright tests in `web/e2e` against it through
`vite preview`: the real WASM backend in its Worker, in Chromium at desktop and phone size, with
the browser in `America/New_York` so school times cannot fall back to the browser's zone. They
cover the home page, the schedule list and week grid, filters, the lesson sheet, the release
countdown, early-published workshops, deep links, German, that an edit, the session and generated
lessons survive a reload until "Reset demo", and that "Use here" moves the demo between two tabs. Each test runs in a fresh browser context, so saved data never leaks
from one test to the next. Any console error fails a test. The
`test-e2e` CI job runs them on every push and uploads the Playwright report when they fail. Run
`just e2e-install` once to download the browser.

Lessons get random IDs when they are generated, so a link to a lesson works only as long as the
saved data that holds it (until "Reset demo" or a new build). Generation creates only lessons that have not started (ADR 0003); the seed
brings the lessons of the week before the visit, so the schedule has a recent past.

## Constraints to keep in mind

- `cmd/wasm` must not import server-only packages (database drivers, SMTP, CLI, `os/exec`,
  `httptest`). `scripts/check-wasm-deps.sh` enforces this in CI.
- Go's WASM runtime is single-threaded. CPU-heavy work blocks the Worker (not the UI), so keep
  request handlers cheap.
- A panic that escapes recovery terminates the Go program. The UI then shows "Demo crashed —
  reload". A reload restores the saved data; if that data is what crashed it, the card's "Reset
  demo" starts over.
- Encoding a snapshot after a change runs in the Worker too: the demo data is about 100 KB of JSON
  and takes a few milliseconds in WASM. Keep the store's tables plain (no derived indexes that
  would bloat the snapshot).
- The binary size is reported in every CI run (`test-web` job summary).
