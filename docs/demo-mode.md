# Demo mode (GitHub Pages)

The live demo at https://cwbudde.github.io/studio-schedule/ runs **without any server**. GitHub Pages
only serves static files, and we don't host a backend for the demo. Instead:

1. The Go application (`cmd/wasm`) is compiled with `GOOS=js GOARCH=wasm`. This is the **same**
   `internal/app.New` handler, services and HTTP API as the production server.
2. The browser starts it in a **Web Worker**. The Worker loads `wasm_exec.js` (copied from the Go
   toolchain that built the binary) and `app.wasm`.
3. The Go side registers `globalThis.StudioScheduleAPI.fetch(request) → Promise<response>`. Each call
   becomes an `*http.Request` that is served by the handler in its own goroutine.
4. The React app uses the same generated `openapi-fetch` client as in production, but with a custom
   `fetch` that posts requests to the Worker. A small cookie jar in the Worker stores `Set-Cookie`
   headers, so session cookies behave as in a real browser–server setup.
5. The Worker saves the whole in-memory store and its cookie jar in IndexedDB after every change, so
   a reload keeps the data and the session until the visitor resets the demo (see below).

## The about page

The demo opens with an about page (`#/about`, `web/src/features/demo/AboutPage.tsx`): what the
app does, how the demo works, what to try per role, and links to the docs. It opens either demo
school ("Two demo schools" below). It is the demo's
entrance and replaces explanations that used to live in the README and the demo banner.

- **When:** the home route (`#/`) redirects to it until the visitor has opened the demo once in
  this browser (`web/src/features/demo/entered.ts`, the localStorage key
  `studio-schedule-demo-entered`). Any page of the app counts as opened, so a deep link or a mail
  link goes straight in and is not followed by the about page later. The banner's "About this
  demo" leads back to it. Without storage (blocked site data) the about page shows on every visit
  to `#/`, and "Open the demo" lets the visitor in for that page load.
- **Bare:** the route has `staticData: { bare: true }`; `RootShell` (`RootLayout.tsx`) renders it
  without the header, banners and footer. It calls no API.
- **No backend yet:** on a first visit the Worker starts when the app's layout first mounts
  (`startBackend()` in `RootLayout`), so the about page downloads no `app.wasm` and takes no tab
  lock. A returning visitor's Worker starts at once (`main.tsx`).
- **Absent elsewhere:** outside the demo build `/about` is a 404 and `/` shows the home page.

## Differences from a real installation

| Aspect     | Production                  | Demo                                                             |
| ---------- | --------------------------- | ---------------------------------------------------------------- |
| Database   | PostgreSQL                  | **In-memory store**, seeded with fictional data on a fresh start |
| Demo dates | Fixed school year 2026/27   | **Relative to the visit that seeded the data** (see below)       |
| Lessons    | Generated by the hourly job | Same job: once before the first request, then hourly             |
| Durability | Persistent                  | **Kept in the browser (IndexedDB) until "Reset demo"**           |
| Email      | SMTP via outbox worker      | Outbox only; shown in the demo mailbox panel                     |
| Passwords  | argon2id, production params | Cheap parameters so login is fast in WASM; seeded demo accounts  |
| Sign-in    | Registered accounts         | The login page lists one demo account per role                   |
| Downloads  | Plain links (iCal, PDF)     | Fetched through the bridge and opened as Blob URLs               |
| Receipts   | typst module run by wazero  | **The same module in the Worker's WebAssembly**, loaded on use   |
| Routing    | Browser history             | Hash history (`/#/…`), because Pages has no SPA fallback         |
| Timezone   | Host tzdata or embedded     | Embedded `time/tzdata`                                           |

Everything else, including validation, permissions, booking rules, the release window, receipts and
the API, is the same code.

## Seed data relative to the visit

On a fresh start (the first visit, after "Reset demo", or after a new build) `cmd/wasm` seeds the
store for the day of the visit (today in the school time zone, from the app's clock) with the
visitor's demo school (see "Two demo schools"): `seed.LoadDemoSchoolAt(ctx, st, today, school)`. A later visit restores the saved data instead, with the dates of
the visit that seeded it: the term and workshops do not move along, and after a few weeks the
workshops lie in the past. "Reset demo" seeds again for today; the banner says so. The demo
term runs from three weeks before that day to about ten months after it, class members join on the
term's first day, and three one-off public workshops follow 3, 17 and 24 days after it. The seeded
class lessons of the week up to the visit carry the members' automatic bookings, and the lesson
generation at startup books the members into every later lesson it creates (ADR 0009), so class
lessons show fewer free places than workshops, which nobody is booked into, except two: a small
tap workshop 10 days after the visit is booked up by members and has two members on its waiting
list (ADR 0010; nobody of the demo logins' families), so the demo shows a full lesson. Alina's
ballet workshop (24 days after the visit, accompanied by Felix) has the participants she added
herself (ADR 0009, amendment): a guest with an email, a walk-in guest without one, and Ute
Tallowfield on a trial with a note. The demo
releases one week ahead, so the later workshops always lie beyond the release window; they are visible
because workshops are published early. `scripts/wasm-smoke.mjs` checks this.

The server (`studio-schedule serve` with `DEMO_MODE=true`, on the memory store) uses `seed.LoadDemo`,
which builds the same data for the fixed `seed.FixedDemoAnchor`: the term is the school year
2026-09-01 to 2027-07-31 on every run, and its workshops lie in September and October 2026.
`studio-schedule seed` uses `seed.LoadDemoSchoolAt` with the same fixed anchor by default
(`--anchor today` or a date moves it, `--school` picks the school). Only the dates differ between
them; names, IDs and the timetable are the same.

## Receipt PDFs

Receipts (ADR 0012) are rendered by the typst module built from `tools/receipt-pdf`
(`internal/pdf/typstwasm/receipt.wasm`, about 24 MB, 8.5 MB gzipped). The server embeds it and runs
it with wazero; the demo build copies the same file to its assets (`scripts/build-wasm.sh`), and
the Worker fetches and compiles it only when the first receipt is rendered
(`web/src/api/wasm/receiptPdf.ts`, a small WASI shim). Go asks for a render through
`__studioScheduleRenderPDF` (`wasmbridge.PDFRenderer`) and waits for its promise; the first render
waits for the download. Random numbers are zeros on both sides, so the demo renders the same bytes
as the server (`scripts/receipt-pdf-smoke.mjs` checks this in CI, and `scripts/wasm-smoke.mjs`
downloads a receipt through the whole bridge). The seeded receipts have no PDF yet: each is
rendered on its first download and then stored, like the original of a receipt sold in the demo.

## Saved data and "Reset demo"

The demo keeps what a visitor does across reloads, in their browser only:

- **What is saved:** a snapshot of the complete in-memory store (`memory.Store.Snapshot`, every
  table but the job runs, which start again on each load; ADR 0020) and the Worker's cookie jar (the session), as one record per demo school in the IndexedDB
  database `studio-schedule-demo` (`web/src/api/wasm/persistence.ts`): `current` for the programme
  school, `current-werkstatt` for the werkstatt school (see "Two demo schools"). Cookies that do not have the
  expected shape are dropped on restore.
- **When:** after every committed change. `memory.Store.OnCommit` runs after each read-write
  transaction that wrote something (by a request or a background job, e.g. the lessons the
  generation job creates); `cmd/wasm` passes `wasmbridge.NotifyChanged`, which calls the Worker's
  `__studioScheduleChanged()`. A response that sets a cookie counts too. Saves are debounced by
  250 ms, so a burst of changes is saved once, and the page asks the Worker to save at once when it
  is hidden or closed (`pagehide`, `visibilitychange`; best effort). The Go side encodes the
  snapshot through `StudioScheduleAPI.snapshot()`: it copies the copy-on-write tables under the
  store's lock and encodes them without it, in one streaming pass.
- **When saving fails** (no quota, IndexedDB blocked in a private window), the visitor sees one
  notice that changes will not survive a reload. When the Go program has exited, the Worker stops
  saving (no misleading notice).
- **Restore:** on start the Worker claims the saved data (below) and reads the record before it
  starts Go, and hands the store to it as `globalThis.__studioScheduleSnapshot`. If IndexedDB fails
  or does not answer within three seconds, the demo starts from the seed, saves nothing, and shows
  the notice. `cmd/wasm` restores it before anything reads the store
  and before the jobs run, and reports `StudioScheduleAPI.restored`. Only then does the Worker load
  the saved cookies and answer requests.
- **Versions:** a snapshot fits only the build and the school that wrote it. Its header names the
  build version (`main.version`) together with the demo school, and a fingerprint of the store's Go types (every table and domain struct), plus
  the snapshot's own format version. `memory.Store.Restore` refuses any other
  (`memory.ErrSnapshotMismatch`): the demo then starts fresh from the seed, and the Worker deletes
  the old record, saved session included.
- **Format:** JSON (`encoding/json/v2`), which the WASM binary links anyway, so persistence adds no
  code to it. Each table is a list of its rows; keys are derived again on restore.
- **Completeness:** every field of the memory store's state needs a codec in
  `internal/store/memory/snapshot.go`; `TestSnapshotCoversEveryTable` fails for a table without one,
  and `TestSnapshotRoundTrip` restores the full demo data (plus a row in each table the seed leaves
  empty) and compares every table.
- **Reset demo:** the button in the header (and on the "Demo crashed" card) asks first, then stops
  the Worker, deletes the current school's record from the page itself (so a crashed or hanging
  Worker cannot block it), and reloads. The demo starts fresh from the seed, for today, signed out;
  the other school's saved data stays. If the delete fails
  or takes longer than five seconds, the page reloads anyway and says that the reset failed.
  Nothing else expires the saved data.
- **One tab at a time:** all tabs of the origin share the IndexedDB record, so only one tab runs the
  demo: it holds the Web Lock `studio-schedule-demo` (`web/src/api/wasm/tabLock.ts`). Another tab
  shows "The demo is open in another tab" with "Use here": it asks the active tab over a
  `BroadcastChannel` to save (it waits up to 4.5 s for that save), stop its Worker and release the
  lock, then reloads into the demo. The previous tab shows the same notice. A tab that does not
  answer within five seconds (frozen in the background) loses the lock by force and stops when it
  runs again. A starting tab waits up to 1.5 s for the lock before it shows the notice, so a reload
  does not trip over its own previous page. Only the tab that holds the lock shows "Reset demo".
  Without Web Locks every tab runs its own demo.
- **Fencing:** in case a tab that lost the lock still saves (it was frozen during the takeover), each
  Worker claims the data on start: one transaction increments the epoch in the record `owner` (one
  for both schools) and reads its school's record. A save checks, in the same transaction as its
  write, that `owner` is still its epoch; otherwise it is refused and that Worker stops saving. A
  reset deletes only the school's record, never `owner`, so stale saves stay refused.
- **The session cookie in IndexedDB:** GitHub Pages serves every project of a user from one origin
  (`cwbudde.github.io`), so other pages there could read the record, cookie included. This is
  acceptable because everything in the demo is fictional and the token opens only that browser's
  own in-memory demo; a real installation never stores sessions this way.

A demo server over HTTP (`serve` with `DEMO_MODE=true`) keeps nothing in the browser and has no reset
button.

## Two demo schools

The demo offers one fictional school per theme (ADR 0018), on the same site: **programme**
("Studio Demo — Ballet & Dance", the app's own look, English) and **werkstatt** ("Tanzhaus am
Lindenhof", the Werkstatt look, German, with a background photo). They share every person and class
(`seed.DemoSchoolAt`); the settings differ (name, theme, accent, language, background, imprint and
receipt issuer; the seeded receipts are the werkstatt school's own, in German), and so do the
places: the werkstatt school has one house with the rooms "Oben", "Unten" and "Trainingsraum".

- **Choosing:** `web/src/features/demo/school.ts`. The page address may name the school outside the
  hash, `?demo=werkstatt` or `?demo=programme` (the README links both). `main.tsx` reads it before
  anything else, removes it from the address (`history.replaceState`), stores the choice and enters
  the demo, so the link skips the about page. The about page has a button per school ("Open the
  demo", "Open in the Werkstatt look"), and the demo banner switches to the other school.
- **Stored choice:** localStorage `studio-schedule-demo-school`, guarded like `entered.ts`; the
  default (and an unknown stored value) is programme. Without storage the choice holds for the page
  load.
- **Switching:** `switchSchool` (`web/src/api/transport.ts`) asks the running Worker to save its
  pending changes (two seconds at most), then stores the new choice and reloads at `#/`: one Worker
  runs per tab, and it serves one school. The about page's button of the school already running
  opens it in place; the other one switches. The persisted query cache (ADR 0017) carries the school in its buster, so the other
  school's copy is discarded rather than shown.
- **Seeding:** the page tells the Worker the school in its first message (`init`, sent by
  `WasmBridge`; a page reads the choice once, so another tab's switch does not change what this
  one resets); the Worker passes it to Go as `DEMO_SCHOOL`, and `cmd/wasm` seeds that school on a fresh start (an unknown value seeds
  programme and logs a warning).
- **Records:** one IndexedDB record per school (above), so each school keeps its own data, session
  included. `current` stayed the programme record, so visitors from before the second school keep
  their data. The snapshot header names the school, so a record is never restored into the other
  school. "Reset demo" resets only the current school.
- **Tab lock:** still one per origin (`studio-schedule-demo`), whichever school a tab shows: both
  schools share the `owner` epoch, and only one Worker runs at a time.

## Accounts and mail in the demo

The demo is a _demo installation_ (`app.Deps.Demo`, also set for `serve` with `DEMO_MODE=true`):

- **Demo accounts:** every seeded account has the published password `demo-password`, and
  `GET /api/v1/demo/logins` lists one account per role (member, instructor, office, admin) for the
  login page. One more is a managed dependent (ADR 0008): Sophie Hollowmere, a teenager with an
  account of her own (`sophie.hollowmere@example.com`), who books her classes herself; the admin
  can also "sign in as" her from Accounts. Another is the accompanist Felix Keysworth
  (`felix.keysworth@example.net`, an instructor account linked to his staff record), who sees the
  participants of the lessons he accompanies; he is not on the login page, which lists the first
  account of each role (Alina Starling for instructors), so he signs in by email.
- **Mailbox:** nothing is ever delivered. `GET /api/v1/demo/mailbox` lists the outbox, and the
  mailbox panel in the header shows it, so a visitor can register, open the confirmation link and
  sign in. The admin's mail log (`/admin/mails`, ADR 0014) lists the same outbox: every mail stays
  pending there, which the page says.
- **Announcements:** the seed has two, written by the office and not emailed: one for everyone, and
  one for the members of the Creative Dance classes, which the demo member sees through her son.
  An announcement the office emails in the demo lands in the mailbox: publishing it wakes the
  `announcements` job, which runs in the Worker too (every minute for scheduled ones).
- **Import and duplicates** (ADR 0015): the office's Import page offers a fictional sample file as
  a download, a Blob made in the browser from the page's own copy
  (`web/src/features/import/members-sample.csv`, kept equal to the tests' file by
  `servicetest.TestSampleCopy`); importing it into the demo creates and updates persons like on a
  server, in the in-memory store. The seed has two pairs of duplicates for the Duplicates page:
  Lena Quillfeather twice with the same email (one with the member number M-1042, which the sample
  updates) and Jonas Brightwater twice with the same name, none with an account.
- **What each role sees:** the demo data has one workshop for members only, one hidden workshop
  (staff only) and a room rental (staff only, ADR 0007, amendment) a few days after the visit
  date. Signing in as the demo member, instructor or admin
  shows the difference. The admin can open Accounts and "sign in as" another account; a banner
  leads back ([ADR 0005](decisions/0005-rbac-and-impersonation.md)).
- **Mail links:** the Worker passes the app's URL (with the `#/` route prefix) to Go as the
  `APP_URL` environment variable. This includes the waiting-list invites
  (`#/waitlist/accept?token=…`), which the `waitlist-expiry` job (every minute, in the Worker too)
  ends when they run out.

Real installations answer both endpoints with 404
([ADR 0004](decisions/0004-accounts-sessions-and-mail.md)).

## The PWA in the demo

The demo is installable too, with a static manifest "Studio Schedule (demo)" that the build
generates, and its service worker is scoped to the Pages path (`VITE_BASE`). It precaches the app
shell but not `app.wasm`, `receipt.wasm` or `wasm_exec.js`: offline after a reload the backend may
not start, and the pages show the last schedule and My lessons from the offline cache, read-only
([ADR 0017](decisions/0017-pwa-and-web-push.md)). Web push has no push service to reach here: the
demo's "subscription" is made up, its push sender hands each notification to the page, and the page
shows it through the service worker, so turning notifications on and getting a waiting-list invite
shows a real notification (after the browser's permission).

## Calendar feeds in the demo

Calendar feeds ([ADR 0011](decisions/0011-calendar-feeds.md)) are created with the same code: the
demo stores the token's hash. No calendar app can reach a link of the demo, since there is no
server, so a demo installation (`Deps.Demo`) answers `createCalendarFeed` without a `url`, only with
the `path`. The UI offers the feed as a download instead: `openDownload` fetches
`/ical/{token}.ics?download=true` through the bridge (any path reaches the Go router, `/ical/`
included) and saves the attachment as a Blob, with the file name from `Content-Disposition`.

## Building it locally

```sh
just demo-serve        # = scripts/build-wasm.sh + vite build --mode demo + vite preview
```

Open the printed URL, for example `http://localhost:4173/studio-schedule/`.

## End-to-end tests

`just e2e` builds the demo and runs the Playwright tests in `web/e2e` against it through
`vite preview`: the real WASM backend in its Worker, in Chromium at desktop and phone size, with
the browser in `America/New_York` so school times cannot fall back to the browser's zone. They
cover the about page (with `test.use({ demoEntered: false })`; every other test starts as a
returning visitor), the home page, the schedule list and week grid, filters, the lesson sheet, the release
countdown, early-published workshops, deep links, German, that an edit, the session and generated
lessons survive a reload until "Reset demo", that "Use here" moves the demo between two tabs, and
the two demo schools (the about page's Werkstatt button, the banner's switch, a booking that
survives a visit to the other school; the fixture option `demoSchool` picks a test's school).
`web/e2e/werkstatt.spec.ts` drives the Werkstatt school (`test.use({ demoSchool: 'werkstatt' })`,
the visitor's language set to English so the shared helpers' names apply): its look (`data-theme`,
the font, the background, and a school without one), the header's sign-in and sign-out, dialogs,
the tabs and the phone menu, the schedule's day bands and room columns, booking and canceling with
a card's square button, home's "My schedule", the account page and taking attendance in the
participants table. Each test runs in a fresh browser context, so saved data never leaks
from one test to the next. Any console error fails a test. The
`test-e2e` CI job runs them on every push and uploads the Playwright report when they fail. Run
`just e2e-install` once to download the browser.

Lessons get random IDs when they are generated, so a link to a lesson works only as long as the
saved data that holds it (until "Reset demo" or a new build). Generation creates only lessons that have not started (ADR 0003); the seed
brings the lessons from the term start (three weeks before the visit) up to the visit, with
attendance, no-shows, late cancellations, guests and trials, so the schedule has a past and the
statistics have weeks to count. Classical Ballet's past lessons have no attendance, so the
instructor and office views show attendance to take.

## Constraints to keep in mind

- `cmd/wasm` must not import server-only packages (database drivers, SMTP, CLI, `os/exec`,
  `httptest`, wazero and the embedded typst module). `scripts/check-wasm-deps.sh` enforces this in
  CI.
- Go's WASM runtime is single-threaded. CPU-heavy work blocks the Worker (not the UI), so keep
  request handlers cheap.
- A panic that escapes recovery terminates the Go program. The UI then shows "Demo crashed —
  reload". A reload restores the saved data; if that data is what crashed it, the card's "Reset
  demo" starts over.
- Encoding a snapshot after a change runs in the Worker too: the demo data (seed, generated lessons) is
  about 450 KB of JSON and takes a few milliseconds in WASM. Keep the store's tables plain (no derived indexes that
  would bloat the snapshot).
- The binary size is reported in every CI run (`test-web` job summary).
